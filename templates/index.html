Why grep fails

grep "#ifdef LEGACY" finds where the guard appears, but can't tell you whether LEGACY is ever defined in any build, or whether the code inside is ever reachable at runtime.

How it accumulates

Feature flags added for A/B experiments. Platform shims for OSes that were discontinued. Rollback guards for migrations that completed. Each one seemed temporary; none got cleaned up.

The Approach

A Four-Phase
Pipeline

The problem needs three completely different views of the codebase — build-system metadata, source-level preprocessor structure, and runtime reachability. Each phase handles one view, then a correlator combines them all.

Phase 1 answers

"Which macros are defined in each build?" Without this, we'd flag code that is active in a different configuration we didn't check.

Phase 2 answers

"Which source lines does each #ifdef guard?" The compiler erases this structure; we must capture it before erasure.

Phase 3 answers

"Which lines can actually run?" Code can compile fine but never be called. Static define-checking alone misses this class of dead code.

Phase 01 · Build System

Reading the
Build Config

Before we can say whether code is dead, we need to know what flags each build target uses. CMake handles this — we just need to ask it correctly.

Background: CMake & build systems

CMake is a build system generator — reads CMakeLists.txt, emits Makefiles/Ninja. A build target is one compiled binary. Each target can use different -DFOO defines that control which #ifdef branches compile.

compile_commands.json — one entry
[{ "file": "feature.cpp",
   "command": "clang++ -DEXPERIMENTAL_FEATURE ..." }]

When CMake runs with -DCMAKE_EXPORT_COMPILE_COMMANDS=ON it writes a compilation database — one entry per compiler invocation. The -D flags buried in each command are exactly what #ifdef checks. Phase 01 extracts every define used by every target, giving Phase 04 the complete map of "what macros are live in any build?"

How it works
1
Run cmake -DCMAKE_EXPORT_COMPILE_COMMANDS=ON. CMake emits compile_commands.json — every compiler invocation in one JSON file.
2
Parse each command for -DFOO / -DFOO=BAR patterns — these are the preprocessor defines controlling which #ifdef branches compile.
3
Infer target name from path: each command contains CMakeFiles/<target>.dir/ — a regex match gives the target→file mapping.
4
Write build_config_map.json: target → {defines[], files[]}. Phase 04 looks up each source file here to find which targets compile it.
No compiler? No problem. If no C++ compiler exists, a fake no-op fake-cxx.sh is generated and passed via -DCMAKE_CXX_COMPILER. CMake still emits full compile_commands.json — nothing is actually compiled in this phase.
produces build_config_map.json

Phase 02 · Source Analysis

Mapping the
#ifdef Guards

The compiler never sees #ifdef blocks — the preprocessor strips them before compilation. So we have to intercept the preprocessor itself before it strips anything.

Background: compilation pipeline

C++ pipeline: Preprocessor (#include, #ifdef) → Compiler (parses C++, emits IR) → Linker. By the time the compiler sees the code, ALL #ifdef structure is gone. We must intercept at the preprocessor stage.

Phase 02 hooks into Clang's PPCallbacks interface — virtual methods that fire for every preprocessor event (Ifdef, Ifndef, Else, Endif). This records the full block structure — macro name, file, and exact line range — before any branch is erased. There is no other way to get this information after preprocessing completes.

How it works
1
A C++ plugin registers a PPCallbacks handler with Clang's preprocessor before parsing begins. Callbacks fire for every directive encountered.
2
The plugin listens to Ifdef, Ifndef, Elif, Else, Endif events. Each reports the macro name and exact source location (file + line).
3
Nesting tracked with a stack: #ifdef pushes a frame, #endif pops and records the complete range. System-header blocks push a sentinel frame so Endif stays aligned.
4
System headers skipped via SM.isInSystemHeader(). Only user code matters.
5
Flushed to ast_mapping.json in HandleTranslationUnit() — not the destructor (fires too late when hosted in-process).
Critical: use -add-plugin, NOT -plugin. Our plugin is CmdlineBeforeMainAction (runs alongside the parse, not replacing it). -plugin expects ReplaceAction type and will reject the invocation.
produces ast_mapping.json

Phase 03 · LLVM IR

Tracing Every
Execution Path

Compiling ≠ running. Code can compile perfectly and still be unreachable at runtime. This phase uses LLVM's intermediate representation to find every function that can actually be called.

Background: LLVM IR & compilation passes
C++ source → clang -emit-llvm -g → .bc files → llvm-link → whole_program.bc → opt + DeadFeaturePass → reachability.json

LLVM IR is a typed, SSA-form, platform-independent assembly language. Every LLVM-based compiler compiles to it. A Module Pass runs on the whole linked module, seeing every function and call. The -g flag embeds DILocation metadata into every IR instruction — the only way to map IR back to original source file + line (the bridge to Phase 02's block map).

By linking all .bc files into one whole-program bitcode file (LTO mode), the pass sees every function and every call edge across all .cpp files simultaneously. BFS from main() marks every reachable function; DILocation metadata then maps each reachable IR instruction back to its source line. Result: a set of {file → reachable lines} that Phase 04 intersects with the #ifdef block map.

How it works
1
Each source compiled to .bc with clang++ -emit-llvm -g. -g embeds file paths + line numbers into the bitcode as DILocation metadata.
2
llvm-link merges all .bc files into whole_program.bc (LTO). Without this, cross-file calls are unresolved symbols — untraceable.
3
BFS seeds: main() + all functions with external linkage. Each wave visits direct callees via CallBase::getCalledFunction().
4
Indirect calls (function pointers, virtuals): conservatively adds ALL address-taken functions to reachable set if any reachable function has a null callee.
5
For every reachable instruction: I.getDebugLoc() → DILocation::getLine() + DIFile → appended to reachable_lines[file].
Why LTO? Without merging bitcode first, a call from main.cpp into utils.cpp looks like an unresolved symbol — un-traceable. LTO makes the entire call graph visible in one pass. New PM (PassInfoMixin<> + llvmGetPassPluginInfo) is required for LLVM 14+.

Phase 04 · Correlator

Dead Code
Identified

Three independent datasets, one final verdict. For each #ifdef block, the correlator asks: is it ever compiled? Is it ever reached? If neither — it's dead.

Background: static dead code analysis

A region is statically dead if it can never execute under any input/configuration — provable without running the program. Our analysis is sound for HIGH findings: if a macro truly never appears in Phase 01, it provably never compiles. No false positives possible.

Join logic: For each block B with macro M, let configs(B) = targets that compile B's file. If M ∉ defines(config) for ALL configs → HIGH. Else if M ∈ defines(config) for some config but B's lines ∩ reachable_lines = ∅ for all such configs → MEDIUM. Otherwise: live. Per-file filtering is critical: targets that don't compile B's file are excluded — they can't make the code live or dead.

How it works
1
For each #ifdef MACRO block (Phase 02): look up MACRO in Phase 01's define map (per-file targets only). Never defined anywhere → HIGH confidence dead.
2
#else branches: inverse check. If parent macro is defined in ALL relevant configs, the #else can never be active.
3
Macro IS defined in some config: cross-reference block lines with Phase 03 reachable set. Zero overlap → code compiles but never runs → MEDIUM confidence dead.
4
build_file_config_sets() maps each source file to only its compiling targets. Unrelated targets excluded — prevents false negatives from targets that never see the file.
HIGH

Macro never defined in any build. Code cannot compile. Safe to delete.

MEDIUM

Macro defined somewhere, but lines never reachable at runtime. Review before deleting.

HIGH confidence

The macro guarding this block is never defined in any known build configuration. This code path cannot possibly be compiled. It is safe to delete the entire #ifdef block with no risk of breaking any build. Zero false positives — if the define doesn't exist anywhere in Phase 01's map, it truly never compiles.

MEDIUM confidence

The macro IS defined in some configuration, so the code compiles — but Phase 03 found that the guarded lines are never reached at runtime from main(). Review before deleting: it may be a callback registered via function pointer (conservatively included) or a safety guard for rare error paths. Check the call graph before removing.

Workflow

1. Remove HIGH findings first — provably safe. 2. Re-run the pipeline after each removal — one dead block can cascade and expose new dead blocks downstream. 3. Tackle MEDIUM findings with a code review. LOC removable is a lower bound: after all removals, the true saving is typically 30–60% larger due to cascading effects.

What the pipeline found
Phase 1 → which macros exist per build config
Phase 2 → which lines each macro guards
Phase 3 → which lines actually run (BFS from main)
Phase 4 → intersection = dead code
Limitations to keep in mind
Indirect calls (function pointers, virtuals) are handled conservatively — over-approximation means some MEDIUM findings may be false positives.
Only analyzes build configurations that CMake knows about. Hidden configs (hand-crafted build scripts) are not considered.
